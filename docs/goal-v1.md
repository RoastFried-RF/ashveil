# ASHVEIL v1.0.0 · X1–X4 구현 Goal

작성: 2026-10-28 15:09 KST. 사용자 지시: “goal로 전부 구현 진행”.

이 파일은 지속 작업의 목표·제약·완료 기준이다. 2026-10-28 사용자가 이 계획을 참조한 `/goal` 지시를 보내 구현을 시작했다. 파일·커밋 저장만으로 전체 목표 완료나 앱의 백그라운드 실행 상태를 추정하지 않는다.

## 목표

`RoastFried-RF/ashveil`의 최신 원격 `main`에서 프로토타입과 X1–X4, 영어 UI/로그/콘텐츠를 포함하는 v1.0.0을 구현한다. 문서와 실제 코드를 대조해 기능·UI/UX·리소스·버그를 수정하고, 큰 작업 묶음마다 검증·push·GitHub Pages 갱신을 완료한다. 한 번의 미리보기 게시를 이 Goal 전체의 완료로 취급하지 않는다.

정본 우선순위는 `CLAUDE.md`, `docs/CANON.md`의 규칙을 적용한다. 실제 남은 범위/출시 조건은 [v1 실행 기준](v1-execution.md), 현재 동작은 [구현 현황](prototype.md), 확장 범위는 [확장 로드맵](expansion-roadmap.md)을 대조한다. 오래된 체크박스나 번역 문자열 개수로 완성률을 만들지 않는다. [현재 코드 대조 장부](goal-code-audit-v1.md)에서 실제 결손과 각 수락 경계를 추적한다. 정본에 기본안이 있는 루틴 구현/수치는 근거를 기록하고 자율 판단한다.

## 닫아야 할 구현 범위

각 행은 기존 기반을 다시 만드는 지시가 아니다. 최신 코드와 검증 근거를 먼저 확인하고 실제 미완료 부분을 구현한다.

## 지속 실행 순서

1. 최신 main과 지침/관련 설계·코드·최신 근거를 대조해 구체적인 미완료 항목과 파일 범위를 정한다. 이미 닫힌 기능은 검증 근거를 재사용하며 실제 결손에 집중한다.
2. 검토 가능한 행동 사슬을 큰 묶음으로 구현한다. 기능·사용 흐름·표현·리소스를 연결하고 진행 상태를 구현/검증/게시로 구분한다. 매 작은 수정마다 전체 회귀를 중복 실행하지 않는다.
3. 해당 경계 검사와 필수 정적/전체 검사를 실행한다. 실제 입력→행동 비용→원래 UID/몸/수량/인원/돈→보이는 화면→저장 복원을 독립 기대 상태와 대조한다. 실패 원문을 남기고 원인을 고친 뒤 새 결과로 재검한다.
4. 검증할 원문을 고정하고 PNG를 각각 직접 검토한다. 브라우저 World·시각·난수를 주입해 성공처럼 만들지 않는다. 초기 fixture와 자연 플레이를 구분한다.
5. 검증한 앱 원문을 main에 반영하고 Pages CI·배포·공개 진입 버전을 확인한다. 검증 범위·커밋·원문 SHA·최초 실패와 재검·남은 제약을 저장소에 기록한다. 동시 변경은 lease/fast-forward 확인으로 보존한다.
6. 한 묶음을 게시한 뒤 다음 실제 미완료 범위로 이어간다. 코드·자동 검증·외부 사람 평가를 별도로 추적한다.

첫 후속 묶음은 v400 표시 기반을 사용해 게임 중 HUD/창·로그/콘텐츠의 영어 경계를 확장하고, 실제 UI/저장 호환 문제를 함께 닫는다. 이후 순서는 발견된 결함의 심각도·의존성·출시 기준을 근거로 조정한다.

## 실행 환경과 병렬 한도

- Node24, pnpm9.15.9, frozen lockfile, 실제 설치한 Chromium을 사용한다. 새 환경은 실제 버전·HEAD·lock SHA·CPU/메모리 한도를 기록한다. 패키지/브라우저 누락을 성공으로 세지 않는다.
- [환경 기록](cloud-development-harness.md)과 [cloud-harness](../tools/cloud-harness/README.md)를 사용한다. light 최대2개. 빌드·Full·World·원정·GPU·Native·freeze는 heavy 단독이며 light와 겹치지 않는다. Full은 `--maxWorkers=2`, 기존4프로세스 World/원정은 단독 실행한다.
- `environment.py`/`plan.py`로 실제 체크아웃 경로의 명시적 계획을 만든다. 공통 잠금·포트 소유권·새 출력 경로·불변본 보호를 유지한다. freeze 중 원문 작성을 멈추고 불변본에서 build/수정을 하지 않는다.
- `.github/workflows/cloud-development.yml`의 새 실행 환경과 release/authoring 검증 범위를 구분한다. 앱 변경 묶음의 Full을 확인하고, 도구만 수정한 경우 같은 앱 Full과 도구 경계 재검을 구분해 기록한다. main의 Pages Full/배포 결과도 확인한다.
- 정책/인증/연결 오류를 우회하거나 보안 보호를 낮추지 않는다. 사용할 수 있는 권한/도구 안의 구현·검증을 먼저 완료하고 실제 차단 항목만 보고한다.

## 구현 불변 조건

- `src/core`는 순수 TypeScript 규칙 엔진이다. DOM/Vue/Pixi 및 비결정 난수/시각/금지된 초월함수를 넣지 않는다. 콘텐츠는 JSON Def와 패치로 관리한다.
- 기존 UID·개수·기억·인구/공급원·돈·저장/로드의 정합과 정보 비공개 경계를 유지한다. 새 필드/규칙은 실제 저장 이행과 구형 입력을 검증한다. 과거에 없던 실물을 소급 지급하지 않는다.
- 프로젝트 게임 개발 스킬의 실제 입력/화면 절차를 적용한다. 캐릭터·보행·무기·자세 제작은 캐릭터 동작 스킬도 적용한다. 아이콘이나 일부 방향/시제품을 전체 동작 원화 완료로 세지 않는다.
- 큰 묶음의 main push/Pages 갱신은 이미 사용자에게 허가받았다. 외부 사람에게 메시지를 보내거나 테스터를 초대하는 행동은 별도 명시적 지시 없이 수행하지 않는다.

## 최종 완료·일시정지 기준

자동 구현/검증을 다음 기준까지 닫는다.

- 위 구현 범위와 정본의 필수 항목을 코드/실행 근거로 대조한 목록이 있으며, 필수 미완료·출시 차단 결함이 없다.
- 타입·린트·Def/Schema·스프라이트·고정 입력·저장 호환·결정론/전체 회귀가 통과한다. 두 데스크톱 크기와 작은 화면에서 실제 조작·저장/로드·사망·은퇴·모든 결말을 검증한다.
- 현재 소스의 동일 시드30판/최대3일 밸런스 회귀와 GDD의1,000판 탐험 기준을 별도로 충족한다. 옛 v310의 중단된1,000판을 재개하거나 작업 상한 종료를 생존으로 집계하지 않는다. 밸런스 변경은 `docs/sim-latest.txt`와 원문/전체 결과를 갱신한다.
- 최종 원문/빌드·검증 근거·재현 절차·테스터용 가이드와 공개 검토 빌드가 준비돼 있다.

실제 사람의30분 플레이/사망 보고서 평가 및 외부 테스터5명 중4명 재플레이 기준은 사람의 증거를 받아야 한다. 자동 구현/검증을 먼저 완료한 뒤 `사람 평가 대기`로 명확히 보고하고 필요한 실제 평가를 기다린다. 봇이나 자동 브라우저로 사람 평가를 통과했다고 기록하지 않는다.

Goal의 최종 완료는 구현·자동 검증·필수 사람 평가가 모두 충족되고 해당 원문으로 v1.0.0 배포를 확인했을 때다. 버전 숫자 변경이나 한 미리보기 게시만으로 Goal을 완료 처리하지 않는다.
